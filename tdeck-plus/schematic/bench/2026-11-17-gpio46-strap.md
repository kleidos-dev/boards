# T-Deck Plus: the GPIO46 strap after a cold power-up and after resets with the rail on (B4)

- Date: 2026-11-17.
- Unit: the bench T-Deck Plus, case closed, slide switch SW1 on, its cell wired through the bench meter's battery lead (relay K1 in series, normally closed), USB from the bench hub.
- Firmware: Kleidos `tdeck_debug`, built from the firmware of 2026-11-17 plus a throwaway probe that was never committed: a console command `PROBESTRAP` that prints `GPIO_STRAP_REG` (0x60004038) and the reset reason, `PROBERESTART` (`esp_restart()`) and `PROBESYSRESET` (`esp_rom_software_reset_system()`). Image `elf_sha=cbc9ea85b81904e5` for the first four rows.
- Tools: the hub's per-port VBUS switch and the meter's `LEAD OPEN FORCE` / `LEAD CLOSE` (K1), which together remove every supply from the board; the debug console over USB Serial/JTAG.
- Settles: T27 (whether R12 4.7k from GPIO46 to V3V can latch the strap high).

## How the value reads

`GPIO_STRAP_REG` holds the strapping pins as latched. Bit 3 is GPIO0 (esptool `esp32s3.py`, `GPIO_STRAP_SPI_BOOT_MASK = 1 << 3`); bit 2 is GPIO46 (ESP-IDF `components/soc/esp32s3/include/soc/boot_mode.h` takes `1xxx` as SPI boot and `00xx` as joint download boot, and the ESP32-S3 datasheet's boot-mode table asks GPIO0 = 0 and GPIO46 = 0 for download); bit 4 is GPIO45 (esptool `GPIO_STRAP_VDDSPI_MASK = 1 << 4`). The ROM prints the same register as `boot:0x..` on its first line.

## What was run and what came back

| Case | How | Reset reason (ROM / IDF) | Strap |
| --- | --- | --- | --- |
| Cold power-up from the cell | hub port cut, K1 opened (`path=none`), 30 s with no supply, K1 closed first, VBUS restored 8 s later | 0x01 POWERON / `ESP_RST_POWERON` | `0x0008`: GPIO0 = 1, GPIO46 = 0, GPIO45 = 0 |
| Cold power-up from USB | the same, VBUS restored first, K1 closed 8 s later | 0x01 POWERON / `ESP_RST_POWERON` | `0x0008` |
| Core reset with the rail on | the flash tool's reset over USB Serial/JTAG, the running image holding IO10 high | 0x15 USB_UART_CHIP_RESET / `ESP_RST_USB` | `0x0008` |
| Software restart with the rail on, three times | `PERIPH ON PERIPHRAIL` (IO10 high), then `PROBERESTART` | 0x0C RTC_SW_CPU_RST / `ESP_RST_SW` | ROM line `rst:0xc (RTC_SW_CPU_RST),boot:0x8 (SPI_FAST_FLASH_BOOT)` each time; register `0x0008` |
| Digital system reset with the rail on, twice | the probe read IO10 enabled and driven high (`io10_en=1 io10_out=1`), then `PROBESYSRESET` (image `elf_sha=d5453f6f49c0ddd4`) | 0x03 RTC_SW_SYS_RST / `ESP_RST_SW` | ROM line `rst:0x3 (RTC_SW_SYS_RST),boot:0x8 (SPI_FAST_FLASH_BOOT)` both times; register `0x0008` |


## Result

- **At a cold power-up GPIO46 latches low**, whether the board comes up on its cell or on USB. Whatever V3V does at power-up, R12 does not pull the strap above its threshold at the moment the chip samples it, so the print's note ("GPIO46 pulled down by default") holds on this unit and the boot mode is SPI boot.
- **A reset taken with the rail on also left GPIO46 low** in every case tried. A software restart is a CPU reset and may not re-sample the straps at all, so those three rows only show that nothing set the bit; the USB Serial/JTAG reset and the system reset are digital core resets, the one the ESP32-S3 ROM samples GPIO46 at (`esp_rom` `efuse.h`, the ROM print control: "GPIO46 ... when digital reset"), taken while IO10 held V3V on, and both read low.
- So nothing to add to the drawing beyond the print's own GPIO46 note (T11). T27 is answered: no case found in which R12 latches the strap high.
- Supporting, not settling: the print's masked power-on coupling (a 22 µF off VDD3V3 through D4 into Q7's base, R68 100K bleed) would switch V3V on for about 2 s after power-up, and R12 would then latch GPIO46 high. The low latch at both cold power-ups agrees with that coupling doing nothing on this unit, as B3 found for the TP_EN path (`2026-11-17-tp-en-edge-detector.md`); it does not say which parts are absent.
- Afterwards the board was flashed with the plain `tdeck_debug` image of the same firmware, no probe (`elf_sha=ca66bc84d47e9af1`); the meter's relays were left on `path=shunt` (K1 closed, K2 open) and the hub port on.
